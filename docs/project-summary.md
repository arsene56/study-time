## 2. 产品目标与范围

### 2.1 核心目标

面向小学 1～6 年级学生及家长，帮助家庭完成从“老师布置作业”到“学生自主完成”的完整闭环：

1. 家长拍摄或上传老师的黑板、白板作业照片，或家长群中的作业截图。
2. 系统通过 OCR 和规则识别不同学科、不同任务类型的作业。
3. 系统按年级默认规则估算难度和用时，不要求家长先做不可靠的人工估时。
4. 系统结合学生最近 60 天的真实完成记录，逐步形成个性化估时。
5. 系统综合作业量、难度、用眼时长、休息、固定作息和当天临时安排生成计划。
6. 家长和学生都可以调整顺序，系统必须立即重新计算每一项的起止时间。
7. 学生在平板或学习机上逐项执行、打卡；家长在微信中实时查看进度。
8. 通过星星、连胜、徽章、皮肤和家庭心愿等奖励，培养学生的自主规划和独立完成能力。

### 2.2 当前产品形态

- **家长端**：微信小程序。家长在自己的微信中录入、确认、整理和排期作业，并查看进度、周报、奖励申请和重要通知。
- **学生端**：优先适配平板竖屏和学习机的 PWA/Web 应用。学生查看计划、开始任务、完成打卡、处理超时、调整顺序、查看周报和奖励。
- **高保真体验原型**：独立的 Sites 演示站，使用浏览器本地示例数据，不连接正式后端。
- **原生 App**：不在当前阶段范围内，待微信小程序和学生端验证成功后再评估。

### 2.3 用户与家庭模型

- 支持一个家庭内多个学生，数据必须严格隔离。
- 家长可通过不同学生的头像或账号直接切换。
- 首次添加成员时需要选择关系，如妈妈、爸爸或学生本人。
- 家长的调整要让学生看到“谁调整了什么”；学生调整后，家长也要看到相应记录。
- 家长和学生对计划顺序都可直接调整，不设置审批门槛，体现培养学生自主性的产品目标。
- 学生设备计划通过家长微信扫码完成绑定；当前原型有模拟流程，真实微信绑定属于阶段 1 的待办。

## 4. 核心业务流程

### 4.1 家长录入与确认

1. 家长选择当前学生。
2. 上传黑板、白板照片或家长群作业截图。
3. 系统创建作业批次并调用 OCR。
4. 系统把文字拆分成学科和任务。
5. 识别结果先标记为“待确认”。
6. 家长可以修改、删除、补充任务；图片模糊或 OCR 无法可靠识别时，可以直接手动录入。
7. 家长确认后，系统自动估时并直接生成当天计划。

### 4.2 自动生成计划

系统需要综合：

- 学生年级。
- 作业学科、类型、难度和预计用时。
- 最近 60 天的个人实际完成记录。
- 固定每周作息。
- 当天临时安排，例如兴趣班。
- 连续用眼时长和休息。
- 目标睡觉时间。
- 睡前应预留的课外阅读、晚间活动和洗漱时间。

产品规则要求睡前预留 **30～60 分钟**。当前正式算法的默认值为 **45 分钟**；后续需要根据当天作业量和家庭设置继续产品化。

若时间不足，系统必须：

- 明确提示预计完成时间和冲突。
- 建议提前开始。
- 建议压缩非作业安排。
- 不隐瞒“可能无法在目标时间前完成”的事实。

### 4.3 学生执行

1. 学生打开今日计划。
2. 一次只进入一个进行中的任务。
3. 学生可以开始、完成或调整任务顺序。
4. 完成方式：
   - 直接点击完成。
   - 可选先拍照上传完成凭证，再点击完成。
5. 每项完成后更新星星、进度、实际用时和剩余计划。
6. 全部完成后触发嘀嘀闪光反馈、完成通知和可能的里程碑奖励。

说明：直接完成、计时和计划更新已进入正式闭环；任务完成凭证上传目前主要在产品约定和原型层，正式后端仍需补齐专用接口和对象存储流程。

### 4.4 超时处理

实际用时超过预估后，系统不能只显示“超时”，而要立刻重算后续安排，并让学生选择：

- **暂时跳过**：当前确实遇到困难，先跳过该项。
- **继续挑战**：学生认为可以继续完成。

无论选择哪项，都必须：

- 更新后续任务的起止时间。
- 更新最终预计完成时间。
- 明确展示前后变化，例如“预计完成时间已由 20:00 调整为 20:30”。
- 将变化同步给家长端。
- 记录操作人和操作类型。

### 4.5 双端调整与实时同步

- 家长端和学生端均可直接调整任务顺序。
- 调整后，任务内容和时间必须同时更新，不能只交换内容而保留旧时间。
- 服务端重排接口要求提交计划内全部项目 ID，且每个项目必须且只能出现一次。
- 服务端按新顺序重新计算所有开始时间、结束时间和计划完成时间。
- 单实例环境使用 WebSocket 发送更新信号，客户端收到后重新拉取数据。
- 多实例生产环境需要 Redis Pub/Sub 或等价消息总线，避免只在单台实例内广播。

### 4.6 周报与激励

- 家长和学生都可以查看周报。
- 周报包括完成率、专注时长、星星、连胜、分学科情况、目标和徽章等。
- 家长可以写鼓励性点评。
- 支持周结算和额外奖励。
- 支持内置虚拟奖励，也支持家长或学生创建自定义奖励。
- 每个奖励可自行设置所需星星数量。
- 学生发起兑换申请，家长可批准或暂缓。
- 星星扣减与兑换状态必须原子化，避免重复扣减或余额不一致。

### 4.7 通知规则

产品只通知重要事件，避免频繁打扰。当前约定的事件包括：

- 关键作业任务完成。
- 计划发生较大变化。
- 明显超时。
- 当天全部完成。
- 学生发起奖励审批。
- 家长批准或暂缓奖励申请。

普通浏览、轻微拖动或每一分钟的计时变化不发送通知。

## 6. 默认估时与个性化算法

### 6.1 年级通用估时

年级 g 限制在 1～6 年级。基础预计分钟数：

| 类型 | 基础公式 |
| --- | --- |
| 背诵/听写 | 10 + 2 × g |
| 口语 | 8 + g |
| 阅读 | 8 + 2 × g |
| 实践 | 15 + 2 × g |
| 美术 | 20 + 3 × g |
| 劳动 | 15 + g |
| 书写/默认 | 12 + 5 × g |

附加规则：

- 作文或小报：增加 15 分钟。
- 试卷、整张或一套：增加 10 分钟。
- 两遍或三遍：增加 4 分钟。
- 最终四舍五入到最接近的 5 分钟。
- 单项估时限制在 5～60 分钟。

### 6.2 个性化估时

统一历史窗口：

- 最近 **60 天**。
- 由 StudyTimeRepository.PERSONALIZATION_HISTORY_DAYS 统一控制。
- 后续修改天数应只改此常量，不在多处写死。

同学生、同学科、同任务类型：

- 至少 2 个样本才开始个性化。
- 最多取 20 条。
- 融合权重为 min(0.8, 0.25 + 0.1 × 样本数)。

仅同学生、同学科的回退：

- 至少 4 个样本。
- 最多取 20 条。
- 融合权重为 min(0.6, 0.2 + 0.05 × 样本数)。

其他参数：

- 个性化画像最多读取 200 条 60 天内样本。
- 样本越旧，权重按 0.88 递减。
- 速度比例限制在 0.5～2.0。
- 个性化结果按 5 分钟取整，最少 5 分钟。
- 估时置信度：4 个样本起为中等，8 个样本起为高。
- 画像状态：12 个样本起为稳定/高，4 个样本起为学习中/中，否则为起步/低。

### 6.3 计划排序

产品主线：

1. 先安排一个简单、较短的热身任务。
2. 再进入高难度任务。
3. 中段安排普通任务。
4. 最后用轻松任务收尾。

当前正式实现的具体规则：

1. 从简单任务中选择预计最短的一项作为热身。
2. 困难任务按预计分钟数从长到短排列。
3. 其余非简单任务保持原始顺序。
4. 剩余简单任务按预计分钟数从长到短排列。

### 6.4 专注与休息

连续专注上限：

| 年级 | 连续高用眼建议上限 |
| --- | --- |
| 1～2 年级 | 20 分钟 |
| 3～4 年级 | 25 分钟 |
| 5～6 年级 | 30 分钟 |

当累计高用眼时长达到对应上限，且后面仍有任务时，插入 10 分钟休息。

计划最后固定加入 10 分钟“检查作业并整理书包”。

## 7. 执行、星星和成长参数

### 7.1 执行规则

- 一个计划同一时间最多只有一个 ACTIVE 状态任务。
- 普通任务完成获得 5 颗星。
- 休息任务完成获得 1 颗星。
- 当前实现中，非休息的日常整理任务也按普通任务获得 5 颗星。
- 完成用时优先采用客户端提交的实际秒数；否则采用服务器计时；仍无数据时采用预计用时。
- actualSeconds 允许范围为 0～43,200 秒。
- “继续挑战”的默认追加时间为 10 分钟。
- 接口允许追加 1～60 分钟。
- 跳过后，尚未投入的剩余时长按 0 处理；若已经产生实际用时，已花费的时间仍会保留在重新排期中。

### 7.2 时间变化与通知阈值

- 计划预计完成时间变化达到或超过 15 分钟，视为较大变化并生成通知。
- 通知列表默认返回 30 条，最大 50 条。
- 当距离睡觉时间不足默认 45 分钟缓冲时，显示时间不足提示。
- 如果预计完成时间已经超过睡觉时间，必须明确提示超时，而不是仅显示一般提醒。

### 7.3 内置徽章

| 徽章 | 达成条件 |
| --- | --- |
| 第一步 | 累计完成 1 项任务 |
| 专注五项 | 累计完成 5 项任务 |
| 三日连胜 | 连续 3 个完整完成日 |
| 本周稳稳的 | 本周完成率达到 90% |
| 专注 120 | 本周专注达到 120 分钟 |

## 8. OCR 规则与状态

### 8.1 OCR 工作方式

- 高保真原型使用预置示例和模拟识别结果。
- 正式后端已接入腾讯云通用印刷体高精度识别 GeneralAccurateOCR 的适配器。
- 腾讯云 OCR SDK 版本为 3.2.25。
- 默认服务地址为 ocr.tencentcloudapi.com。
- 默认区域为 ap-guangzhou。
- 若未配置云密钥、调用失败或结果不可解析，批次进入 NEEDS_MANUAL_ENTRY。
- 家长可以手动新增、编辑和删除任务。
- 识别后的任务仍为待确认，不能未经确认直接成为不可修改的正式计划。

### 8.2 OCR 置信度

| 平均置信度 | 等级 |
| --- | --- |
| 大于等于 90 | HIGH |
| 75～89.99 | MEDIUM |
| 小于 75 | LOW |

正式数据保存：

- OCR 原始文本。
- 腾讯云请求 ID。
- OCR 服务提供方。
- 平均置信度。
- 每项拆分任务的置信度。

### 8.3 真实上线前仍需验证

- 老师手写黑板、白板照片的真实识别效果。
- 家长群压缩截图、长截图和带表情/水印内容。
- 倾斜、反光、模糊、低光和多栏布局。
- 多学科混排、序号和日期误识别。
- OCR 失败、超时、限流和费用控制。
- 真实样本的人工标注集与准确率验收标准。

## 9. 技术架构

### 9.1 正式业务工程

| 模块 | 目录 | 技术 |
| --- | --- | --- |
| 家长端 | apps/parent-miniapp | Taro + React + TypeScript，支持 H5 调试和微信小程序构建 |
| 学生端 | apps/student-pwa | React + Vite PWA，平板竖屏优先 |
| 共享模型 | packages/shared | TypeScript 类型、接口模型和客户端共享约定 |
| 服务端 | server | Java 21 + Spring Boot 4.1.1 + Maven Wrapper |
| 关系数据库 | docker-compose.yml | MySQL 8.4 + Flyway |
| 缓存/消息 | docker-compose.yml | Redis 7.4 |
| 对象存储 | docker-compose.yml | MinIO，本地模拟 S3/COS/OSS |

### 9.2 高保真 Sites 原型

- 根目录保留最初的高保真可点击原型。
- 技术为 Vinext 1.0.0-beta.5 + React 19.2.6。
- 使用浏览器本地示例数据。
- 不连接正式 Spring Boot、MySQL、Redis 或腾讯云 OCR。
- 主要用途是产品体验、交互验证和公开演示，不应被误认为生产环境。

### 9.3 实时同步

- 当前服务端提供 WebSocket 更新信号。
- 客户端收到信号后重新读取最新计划、活动或通知。
- 当前实现适合单实例。
- 生产多实例部署必须接入 Redis Pub/Sub 或其他消息总线。
- 浏览器 WebSocket 无法方便地设置 Authorization 请求头，因此当前演示通过查询参数传递访问令牌。
- 生产环境必须改为 WSS，并使用短时、一次性的 WebSocket ticket，避免长期访问令牌出现在 URL、日志或代理记录中。

## 12. 安全和质量基线

### 12.1 已完成的安全基础

- API 使用 Bearer 不透明会话令牌。
- 服务端只存 SHA-256 令牌哈希。
- 业务身份从服务端会话解析，不信任客户端提交的身份。
- 家庭和学生级对象访问隔离。
- 家长专属操作和学生仅操作本人数据的授权校验。
- WebSocket 校验身份、Origin 和学生归属。
- 请求 ID、安全响应头和统一错误格式。
- 图片仅允许 JPG、PNG、WebP，并校验文件签名，不只依赖扩展名。
- 对象键由服务端生成。

### 12.2 生产必须遵守

- 所有公网接口使用 HTTPS，WebSocket 使用 WSS。
- 密钥、密码和令牌不得提交到 Git，也不通过普通聊天传递。
- 本地开发默认密码必须在生产替换。
- 使用云厂商密钥管理或部署平台 Secret。
- 腾讯云 OCR 使用最小权限 CAM 子账号，不使用主账号永久密钥。
- CORS 生产环境必须使用明确的 HTTPS 域名白名单。
- 文件上传需要限流、大小限制、内容校验和恶意文件防护。
- 建立未成年人数据授权、导出、删除和留存机制。

### 12.3 当前上传限制

- 单文件最大 10 MB。
- 单次请求最大 12 MB。

## 22. 当前已知边界与风险

- 在线 Sites 原型是浏览器本地数据，刷新、缓存或设备变化可能影响演示状态，不代表正式数据可靠性。
- 腾讯云 GeneralAccurateOCR 更偏印刷体，老师手写黑板的识别质量必须用真实样本验证，必要时需要替换或组合手写识别模型。
- 当前 WebSocket 为单实例信号机制，多实例前必须接消息总线。
- Redis 虽已搭建，但未成为当前核心业务依赖。
- 任务完成凭证、固定作息和临时日程尚未完成正式闭环。
- 真实微信登录和扫码绑定仍未实现。
- 独立管理后台、运营工具和正式 API 文档尚未建设。
- 个性化估时需要足够样本；新用户阶段仍主要依赖年级通用规则。
- 真实生产涉及未成年人数据，隐私、监护人授权和删除机制是上线硬门槛。
- Node 版本需要在本项目终端明确切换为 24，不能依赖用户其他项目的 Node 14 默认环境。
- 历史 Flyway 文件中的 child 字样是迁移历史例外，不能为“全文零命中”而破坏已执行迁移。

## 23. 完成标准

阶段 8 可视为达到首轮上线条件，至少应满足：

- 家长可用真实微信身份创建家庭并绑定学生设备。
- 家长上传真实照片后可获得可修正的识别结果并生成计划。
- 学生完成、超时、跳过、继续和重排都能正确更新后续时间。
- 家长与学生在不同设备上能稳定看到一致状态和清晰的操作来源。
- 多家庭、多学生权限隔离通过自动化和人工测试。
- 星星、周报、奖励申请和审核账目一致。
- 重要通知可达且不过度打扰。
- 生产数据进入 MySQL、Redis 和私有对象存储，备份可恢复。
- HTTPS/WSS、密钥管理、限流、监控和告警生效。
- 隐私政策、监护人同意、删除和注销流程可用。
- 真实 OCR 样本达到双方约定的准确率和人工修正成本。
- 小程序通过审核，小范围灰度稳定后再扩大。
